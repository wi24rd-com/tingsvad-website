The machine room

How the ford is built. Colophon, not fiction.

How the ford is built

For the technically minded: the thing runs on Cloudflare’s platform, from DNS to artificial intelligence, without a single server anyone has to watch. That suits the thing. It has never watched anything. The site is thereby also an open demo of what can be built on Cloudflare Workers and the rest of the platform – with the source code freely available.

Colophon, not fiction. Everything below is what the site actually uses. The source is on GitHub.

Layer 1 of 7 · 8 cards

The edge

Name, shields and access in front of everything.

Before a single line of the thing’s code runs, Cloudflare’s network has already looked up the name, picked the nearest data centre, encrypted the connection and filtered out attacks and bots. The edge is everything that happens in the first milliseconds, close to you.

DNS and domain

The name lives on Cloudflare's name servers

tingsvad.dk has been the family's since the 90s. Today Cloudflare's anycast DNS (sid and val) answers for the name from hundreds of cities at once, so the lookup happens close to whoever asks. The zone is signed with DNSSEC (ECDSA P-256) and the DS record sits with Punktum.dk, so a validating resolver can reject forged answers. Traffic to the site is proxied through Cloudflare, so the real IP addresses behind the Workers are never shown.

Network and security

HTTP/3, HSTS, CSP and no third parties

Everything is served over HTTP/3 from Cloudflare’s network with HSTS. The Content-Security-Policy allows only the site’s own scripts and Turnstile; AI text is always escaped and never becomes HTML. Sessions are a signed, HttpOnly cookie with no personal data. Web Analytics counts without cookies.

DDoS, WAF and analytics

A guard that is on before anyone asks

Cloudflare's DDoS protection stands in front of all traffic with no setup, and the managed WAF ruleset stops known attack patterns before they reach the Workers. The defences show every hour what it has stopped, and the crawlers which bots came by. Web Analytics counts visits with a small script from Cloudflare's own domain, with no cookies, fingerprinting or third parties. The thing's own visitor counter at the bottom of the page is a daily hash in KV (see the Workers KV card) and knows nothing about who you are. Network Error Logging (NEL) reports connection failures back to Cloudflare, so the site can see when something does not arrive.

Rate Limiting + Turnstile

One vote at a time, preferably from a human

Workers’ built-in rate limiting binding counts calls per session and endpoint inside Cloudflare’s own network. The guestbook and the stool application are protected by Turnstile, an invisible bot check with no picture puzzles; the token is validated server-side and can be used only once.

request.cf

The edge knows where it stands

Every request carries a cf object from Cloudflare: data centre, protocol, TLS version, measured round-trip time and much more. A small route in the site Worker, /api/kant, reads four of the fields and sends them back to you, so you can see which of Cloudflare’s data centres answered (your way here). IP, city, country and provider are in the object too; the thing does not read them, and nothing is stored.

Workers Cache

The paper is printed once and read many times

Today's paper, radio, audit and the diaries are the same for everyone, so they are cached in front of the Worker with Cache-Control: public, a Cache-Tag and an ETag from the content. The next guest gets the answer from the edge cache without the Worker running; afterwards it revalidates with If-None-Match and an empty 304. When Cron has printed a new edition, the Worker calls ctx.cache.invalidate({tags}). “Show the machinery” says whether the answer came from the cache (HIT) or from the Worker.

Web Crypto · ML-DSA-65

A certificate that holds against a quantum computer

The certificate of attendance is now signed by the Worker with ML-DSA-65 (FIPS 204), which Workers' Web Crypto offers behind the flag webcrypto_modern_algorithms. The signature is 3,309 bytes, the public key is open at /api/ting-ai/bevis/noegle, and the page can show that a changed name makes the check fail. The case of the cow is still adjourned.

Secrets Store

The keys in one cupboard

The GitHub token, the Realtime token, the webhook secret and the certificate's private key can live in the account's shared Secrets Store instead of as secrets on each Worker. The code asks the cupboard first (env.X_STORE.get()) and falls back to the old Worker secret, so the move can happen one key at a time. Jan sets the keys; they are never in the repo.

Layer 2 of 7 · 5 cards

Delivery

The site itself: static files and a Worker that only wakes up when it is needed.

The pages are ordinary files sent straight from the edge. Only when a page needs its header, language or an API answer does the site Worker wake up, do its work in the same request and go back to sleep.

Workers Static Assets

Static site, no build step

The whole site is one Worker, tingsvad-site, with the files as Static Assets. Every push to main becomes a new release on the global network through Workers Builds. No build: the HTML, CSS and JavaScript sit in the repo exactly as served. Images, scripts and stylesheets are sent straight from the edge without waking the Worker, and they cost nothing. _headers sets the Content-Security-Policy, Permissions-Policy and cache rules; site-worker/wrangler.toml holds the bindings.

run_worker_first

Server logic next to the files

A list of patterns decides when the Worker answers before the files: the HTML pages, /api/*, /admin/* and /sag/*, but not /assets/*. A small router without dependencies (site-worker/index.js) passes the guestbook (/api/sager), the counters and the shareable cases (/sag/980-0007 with link previews) to the same small modules as before and fetches everything else from the files through env.ASSETS. It all happens in the same request, in the data centre nearest you.

HTMLRewriter

One navigation, no build step

The pages are plain HTML files with placeholders. A middleware (functions/_lib/side.js) streams each page through HTMLRewriter and inserts the top bar, navigation and footer from /partials/, fills in the language switch from the page’s hreflang and marks the page you are on. run_worker_first keeps images and scripts away from the Worker, and because _headers only applies to responses straight from the files, the middleware sets CSP and HSTS on HTML itself. Old links such as /#gaestebog are forwarded by a small script to the sub-page where the element now lives.

Content negotiation

Markdown for the machines

If a client asks for Accept: text/markdown, or adds index.md to a page’s address, the middleware answers with the page’s content as Markdown: title, description, canonical address and language versions as YAML front matter, then the text without navigation, scripts and decoration, plus the header x-markdown-tokens with an estimate of its length. Cloudflare’s built-in Markdown for Agents needs the Pro plan; the thing is on Free and does it itself with a small parser without dependencies (functions/_lib/markdown.js). Browsers never send text/markdown and get HTML as always; the response carries Vary: Accept, so no cache mixes the two up.

The error board

Errors both kinds of guest can read

A page that does not exist gives humans the thing’s 404 page in the right language, with links to the five pages. Machines that ask for application/problem+json get an RFC 9457 response with type, title, status, detail, instance, retryable and suggestions; application/json gives the site’s own error contract, and text/markdown gives front matter with http_status and retryable, following the pattern of Cloudflare’s own error pages. Everything under /api/ always answers JSON. If something below the middleware fails, it answers 503 with Retry-After, never 502.

Layer 3 of 7 · 10 cards

Compute

The thing’s machines in a Worker with no address of its own.

Everything that needs more than sending a file happens in the machine Worker behind a service binding: votes, applications, printing the paper and raven post. This is where the long processes live that must be able to sleep, wake and carry on without losing the thread.

Workers + Service Binding

The thing’s machines behind /api/ting-ai/

The thing's machine park lives in a separate Worker. The site Worker calls it through a service binding, a direct call between two Workers that never touches the public internet. The machine Worker has no address of its own.

From Pages to Workers

Moving day

From round 1 to 10 the site lived on Cloudflare Pages. Pages published the whole repo, so even worker/wrangler.toml and the tests could be fetched from tingsvad.dk. In round 11 the site moved to Workers Static Assets: an .assetsignore keeps everything but the site out, so only what guests are meant to see is published. The middleware from functions/ was not rewritten but moved into shared modules that both Pages and the Worker could run while the move was under way. Every branch now gets a Worker Preview with its own bindings, its own KV and its own machine Worker, so a test never writes in the thing’s real minutes. The move was tested by comparing every page in both languages with what Pages served, byte for byte. Only the fonts and the analytics script differed, and those are the zone’s own additions.

Durable Objects

One truth about seven seats

The Great Vote is one Durable Object per ford with WebSocket Hibernation: every connection talks to the same instance, seats are assigned atomically, and the object sleeps between messages without losing the round. A reconnect gives you the same seat, not a new vote. The same technique carries the shared stool: one stool for the whole internet, where the server owns the position and rate-limits every guest.

Workflows

The bureaucracy sleeps durably

A stool application starts a Workflow instance that sleeps a minute, two hours and a day between its steps. It runs while your browser is closed, and every step is idempotent: a repeated step never moves the case two places.

Workflows + Browser Run

Documents and audits, step by step

The raven exchange’s Workflow goes from received via the raven is flying to the document is being written (a PDF from a fixed, escaped template in Browser Run, filed in R2) and delivered; every step is an idempotent transition in D1, and the writing is retried. The audit is another Workflow that each morning takes one page at a time with a pause in between, staying within Browser Run’s free allowance.

Cron Triggers

The paper is printed once a day

An hourly schedule in UTC with a date guard in Europe/Copenhagen, so daylight saving never yields two editions. A job lock in D1 ensures two simultaneous triggers still print one paper per language. Page views never generate anything.

Queues

The raven’s mailbag

Orders to the raven exchange go into the queue tingsvad-ravn. The queue delivers at least once, with retries and a dead-letter queue; because every Workflow instance has a fixed name (ravn-<job>-<attempt>), a duplicate delivery does no harm. Queues are free on Workers Free.

Email Workers

Raven post on a domain of its own

Email Routing applies to a whole zone, so the raven got an old domain of its own: on sitesite.dk, Cloudflare Email Routing hands letters for brev@ straight to the Worker’s email() handler. It parses the letter with postal-mime and keeps only the subject, a short excerpt and the time; the sender becomes a hash, and addresses and links are removed from the excerpt. Nothing is forwarded, nothing is answered, and a letter is shown only if the sender asked for it and it has been approved.

Agents SDK + Workers RPC

The thing as an MCP server

A small Worker on mcp.tingsvad.dk speaks the Model Context Protocol with createMcpHandler from the Agents SDK: a fresh McpServer per call, no state and no Durable Object. The tools call the thing’s Worker through a service binding to a named RPC entrypoint (TingMcp), which runs quotas in D1 and talks directly to the Durable Objects of the vote and the stool. The public /api proxy only reaches the Worker’s fetch() and cannot reach the entrypoint. Connect your assistant.

Realtime SFU + Durable Objects

The radio goes live

On the radio page you can listen live, together with everyone else. A Durable Object makes today's English broadcast as raw audio (Aura-2, 48 kHz) in R2 and asks Realtime SFU for a WebSocket adapter; the SFU calls back to the object, which sends the audio in real time as small protobuf packets. Every listener subscribes to the same track over WebRTC and hears the same point in the broadcast. Listening only: the site's Permissions-Policy blocks the microphone. Realtime is free up to 1,000 GB of egress a month.

Layer 4 of 7 · 6 cards

Data

Where the thing remembers, as well as it can.

The thing’s memory is split by what it has to remember: quick counters in KV, cases and quotas in an SQL database, files in R2 and meaning in a vector index. None of it stores who you are.

Workers KV

Guestbook and counters

A globally replicated key-value store holds the cases raised, the attempts to decide the case and today’s visitors, the last as daily hashes that expire after two days. No cookies for that; the session for the machine park is the only cookie, and it holds nothing about the person.

D1

SQLite at the edge

Newspaper editions, cases, quotas, idempotency keys and rate limits live in a D1 database in Western Europe. Reservations carry a lease, so a crash mid-call never locks the day’s allowance forever.

R2

Media without egress fees

Fictional finds and the radio’s audio files are stored in an R2 bucket under a key of choices, language, prompt version and model. The same combination is therefore fetched from the model only once; every guest shares the file.

Vectorize

Mímir’s archive as a vector index

The editorial corpus (characters, case files, the real facts with sources) is indexed as embeddings from bge-m3. Mímir finds the nearest excerpts to a question and may only quote them. The puzzle’s solutions are not in the index; the server still selects them by spoiler level. The lost property office has its own namespace with a fixed catalogue, so the answers always come from the catalogue and never from the model.

Analytics Engine

The thing’s counting works

The middleware writes one data point per page, the Worker one per machine call and one per event (a moved stool, a vote cast, the day’s audit) to the dataset tingsvad_taelle. A data point is a kind, a name, a language, a data centre and two numbers: no IP, no cookie, no session. Writing does not hold up the response. The Worker reads the numbers with the Analytics SQL binding, without an API token, and keeps the answer for five minutes. Under heavy traffic Analytics Engine samples and weights the numbers back; at the thing’s traffic they are practically exact.

Durable Objects · SQL

The stool keeps a diary

The stool and the vote are Durable Objects with SQLite storage, and now they use it: every move, vote and closed round becomes a row in the object's own table (ctx.storage.sql), with weekday and hour in Danish time. The stool and the vote show the statistics and the SQL that made them. Only time and kind, never who. Rows older than half a year are cleared.

Layer 5 of 7 · 5 cards

AI and browsers at the edge

Models and a headless browser, all behind bindings.

Language models, image models and a real browser run inside Cloudflare’s own network and are called through bindings with no API keys in the code. Every call has a daily quota, and the answers are validated before anyone sees them.

Workers AI

Three models, one budget

Courtroom, Mímir, newspaper and provenance: Llama 3.3 70B in JSON mode, so replies are validated against a schema before they are shown. The image evidence: Llama 3.2 Vision describes, the text model translates. The forge: FLUX.1 schnell. Daily quotas are reserved in the database before the model is called.

AI Gateway

One gate in front of every model

Every AI call passes through AI Gateway, which logs model, latency and tokens, caches identical calls (the same sample picture is described only once) and can set its own ceiling. The site’s own daily quotas still apply; the gateway is the safety net around them.

Browser Run + Images

A browser at the edge

Link previews of a shared case (/sag/980-0007) are drawn as a real image by a headless browser and stored in R2. The minutes can be fetched as a PDF from the same browser. The Images binding normalises uploads in the image evidence: orientation, metadata and size, before the model sees the file.

AI Search

Ask the archive

The ready-made counterpart to the hand-built Vectorize archive: Cloudflare AI Search with built-in storage. The Worker creates two instances itself (Danish and English) through a namespace binding and once a day puts in the site’s Markdown versions, but only the pages whose SHA-256 has changed. Ask the archive searches hybrid (vector and keyword), and Mímir answers with the text model only from the excerpts found and links to the sources. AI Search is billed from November 2026 with 1,000 queries a month included, so the thing has a hard daily quota of 25.

Web Search API

From abroad in the Tingsvad Gazette

When the paper is printed, the Worker can fetch a few real, harmless headlines with env.AI.websearch through AI Gateway and let the language model comment on them in the thing's tone. Headline, source and link come from the search, never from the model, and only happy news gets in: a word list removes anything serious before the model sees it, and the model has to approve each story as purely positive. The searches are paid with AI Gateway credit, and the Worker searches at most twice a day (WEBSEARCH_ENABLED).

Layer 6 of 7 · 2 cards

Your browser

What never leaves your machine.

Some of the thing never runs on a server at all. The cauldron, the sounds, the excavation and your finds live in your own browser under a strict CSP and are never sent anywhere.

Web Workers + CSP

The guest’s code in a closed cauldron

The site’s CSP does not allow eval. The cauldron therefore runs the guest’s function in a Web Worker from a file on the site itself, which has its own narrow CSP in _headers: default-src 'none' (no network) and 'unsafe-eval' only there. The main page stops the worker after two seconds. Nothing is sent to the thing – it is honestly labelled “runs in your browser”.

Outside Cloudflare

What the browser does itself

A service worker for offline and “add to home screen”, Web Audio for the river and the wind, canvas for the excavation and the certificate, the Intl API for Danish dates and seasons, localStorage for your finds.

Layer 7 of 7 · 5 cards

Tooling and quality

What keeps the rest honest.

Measurements, fixed numbers and automated tests make sure that what the site claims about itself is also true. Every morning Gudrun goes through the pages, and faults become issues on GitHub.

Server-Timing

Show the machinery

Every panel in the machine park can unfold its machinery: the products behind it, the actual call, the response time measured in your browser and the Worker’s own measurements of D1, Workers AI, R2, KV and Vectorize, sent as a Server-Timing header. Bindings are wrapped in a small proxy (worker/src/lib/timing.js), so the measuring happens in one place. Stored results are labelled Stored result, so it is always clear whether something is live.

One canon

Dates and rulings in one place

assets/kanon.json holds the universe’s fixed figures: the thing convened in 980, the three rulings with the latest in the 1990s, foggy days and summer. The page reads the file, and Wrangler bundles the same file into the Worker on deploy, so the newspaper’s FACTS and the front-page counters cannot drift apart. A number guard removes sentences with figures the model made up.

GitHub Actions + Playwright

Gudrun checks the browsers too

After every release a test suite opens every page in both languages in the three browser engines (Chromium, Firefox and WebKit, which powers Safari) and as an iPhone, iPad and Pixel, in light and dark theme. It checks that no page scrolls sideways, that there is exactly one heading, that images and the site’s own files load without errors, and runs the axe-core accessibility check and Lighthouse. The first run found weak contrast in the light theme, a page 148 px too wide on mobile and a link without a name for screen readers; all three are fixed. The tests only read; they submit nothing. The tests and the runs are public, and the general part can be reused on other sites.

Workflows + GitHub REST

Gudrun files cases on GitHub

When the audit has failures, its last step opens one issue per day in the repo with the failed pages: path, HTTP status, missing elements and the number of JavaScript errors, never internal error texts. Before opening one she lists the open issues and looks for an invisible date marker, so a retried step does not file the same case twice. When a later audit passes in full, she comments and closes it herself. The token is fine-grained (Issues only, on one repo) and kept as a Worker secret. If GitHub fails, the audit still finishes. See Gudrun’s issues.

Workers Issues + Traces

Errors in production go to Gudrun too

All three Workers have Workers Issues and Traces turned on: runtime errors are collected and grouped, and a share of calls is traced all the way through the bindings. An automation sends new errors as a webhook to /api/ting-ai/gudrun/issues; Gudrun checks the secret, strips anything that looks like a key, and gathers the day's errors in one GitHub issue, at most 20 a day.

Your way here

Two small measurements, both real: where on Cloudflare’s network the page came from, and what the thing has counted in the last 24 hours. Neither knows who you are.

For the machines

Every page also exists as Markdown, and the thing’s errors answer in a format a machine can read. Try it:

The thing as an MCP server

Your AI assistant can connect straight to the thing. The address is https://mcp.tingsvad.dk/mcp, and no login is needed. The assistant can look things up in the minutes, search the lost property office and read the guestbook. If you ask it to, it can also raise a case, vote in the Great Vote and move the shared stool while the guests on the site watch it happen.

The server is a small Worker of its own, built with Cloudflare’s Agents SDK (createMcpHandler, Streamable HTTP). It keeps no state between calls. All logic, all quotas and all data live in the thing’s own Worker and are reached through a service binding to an RPC entrypoint that the public /api proxy cannot reach. Each client is recognised only by a SHA-256 fingerprint of IP address and date, so the fingerprint changes every day and the IP address never leaves the MCP Worker.

How to connect

Claude: Settings → Connectors → Add custom connector, and paste the address above. Other clients that only speak locally (stdio) can use a bridge: npx mcp-remote https://mcp.tingsvad.dk/mcp. Try it in the browser with MCP Inspector: npx @modelcontextprotocol/inspector, choose Streamable HTTP and paste the address.
